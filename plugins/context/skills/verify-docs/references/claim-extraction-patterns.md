# 主張の抽出パターン

現実と照合できる記述はすべて主張として扱う。

## 主張とみなすもの

- パス: 文中のファイル・ディレクトリ・URL は「存在する」という主張
  - 例: 「`plugins/` に plugin のコードがある」→ `plugins/` を Glob
- コマンド: スクリプト名やシェルコマンドは「その通りに動く」という主張
  - 例: 「`bun run check` で lint する」→ `package.json` の `check` を読み、何を呼ぶか確かめる
- 件数: 「skill が 5 つ」のような数
  - 例: `skills/*/SKILL.md` を数える
- 一覧の各項目: 名前と説明の対応は項目ごとに別の主張
  - 項目が実在するか、説明が実体と合うか、を項目ごとに確かめる
- ツール名・バージョン: 陳腐化しやすいので、`package.json` や設定ファイルと一次情報（公式ドキュメント、リリースノート）で確かめる
- 相互参照: 「CLAUDE.md は `@AGENTS.md` だけを含む」のような他ファイルの内容への言及
- ワークフローの記述: 「pre-commit で lint が走る」のような処理の流れ
  - 設定（`.husky/`、`lint-staged`、CI の workflow など）を読み、各段階が実在するか確かめる
- 前提条件: 「全 plugin は mutils を前提とする」のような依存関係

## 判断が要るもの

- 主観的な記述（「整理された構成」）は主張ではないので扱わない
- 将来の予定（「X に対応予定」）は現状と照合できないので UNVERIFIED とし、その旨を書く
- 条件付きの記述（「X が入っていれば Y が動く」）は、条件の仕組みと結果の両方を確かめる
- 暗黙の網羅性: 見出しの下の一覧は「これで全部」という主張でもある。実体側から数えて、一覧に無い項目を探す

## 優先順位

時間が限られるときは次の順に確かめる。

1. パスの存在（速く確かめられ、誤りの影響が大きい）
2. コマンドの挙動（読んだ人が直接実行する）
3. 件数と一覧（網羅漏れが多い）
4. バージョン（古くなりやすい）
5. ワークフローの記述（確かめにくいが、誤りは混乱を招く）
