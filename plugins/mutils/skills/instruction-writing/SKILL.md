# エージェント向け指示の書き方

対象: `$ARGUMENTS`

現行の Claude は指示を字義どおりに、よく守る。そのため、強い言い回しや網羅的な禁止は過剰反応を招き、書いていない範囲には指示を広げない。ここでの書き方はそれを前提にしている。根拠は次の公式文書で、迷ったら原典を読む。

- [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5) と、そこから継承される [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Claude Code の [memory](https://code.claude.com/docs/en/memory) / [skills](https://code.claude.com/docs/en/skills) / [best practices](https://code.claude.com/docs/en/best-practices)

## 何を書くか

- 各行について「消したら Claude が間違えるか」を問い、間違えないなら消す。指示文書は毎回コンテキストに載るので、経緯や弁明ではなく、何をするかを書く
- 優先して書くのは、そのプロジェクト固有の規約、コードを読んでも分からない落とし穴、実行すべき正確なコマンド
- 毎回例外なく守らせたい処理は、文書ではなく hook・lint・CI にする。文書の指示は助言で、守られる保証がない
- 決定的な処理（取得・変換・検証）はスクリプトにし、文書には何を実行して出力をどう使うかだけを書く
- 時期で変わる情報（日付つきの注意、修正済みの不具合の回避策、特定モデル向けの回避策）は書かない

## 旧モデル向けの補助を書かない

現行モデルは自分で検証・修正・進捗報告をし、考える量は effort で決まる。次の指示は過剰な検証や冗長な出力を招くだけなので書かない。

- 「最後に必ず検証する」「double-check する」「サブエージェントで検証させる」。検証させたいなら、実行するテストコマンドや完了条件を具体的に書く
- 「深く考えて」「step by step で」「推論を書き出して」「`<thinking>` タグで考えて」。推論を応答本文に書かせる指示は reasoning_extraction として拒否されることがある
- 「N 回ツールを呼ぶごとに進捗を要約する」のような一律の報告指示。現行モデルは自分から進捗を報告する。頻度や形を変えたいときだけ、報告のタイミングと形を具体的に書く
- 「迷ったら必ずこの skill を使う」「すべての X でこれを参照する」。過剰に発火する原因になる

## 1 つのルールの形

ルールは「条件 → 行動 → 理由」で書く。

- 条件: 読み手が真偽を判定できる形にする。「重要な変更のとき」ではなく「公開 API のシグネチャを変えるとき」
- 行動: その 1 行だけで何をするかが決まる粒度にする。「適切に対応する」ではなく「CHANGELOG に破壊的変更として追記する」
- 理由: 1 文添える。Claude は理由から適用範囲を汎化できる。ルールを裏返しただけの理由（「確認する。確認しないと困るため」）は書かない。書くべきなのは非自明な仕組みや制約（「この CLI は stdout を JSON として解釈するため、ログは stderr に出す」）
- 1 行に 1 つの判断だけを書く。例外は同じ行に詰め込まず、別のルールとして書く
- 常に適用するルールなら条件は省いてよい

```text
悪い: テストはなるべく書くこと。
良い: 公開関数を追加・変更したら、同じディレクトリの *.test.ts にテストを追加する。リリース前の CI がこのファイルだけを実行するため。
```

## 語調と表現

- 平叙の命令文で書く。大文字の MUST / CRITICAL、「絶対に」「必ず」による強調は使わない。多用すると本当に重要な行が目立たなくなる。強調は、書いても守られないことを観察した 1 行にだけ使う
- 禁止だけでなく、代わりに何をするかを書く。「X しない」より「Y する（X だと〜になるため）」
- 要求の強さは言葉で表す。既定は「〜する」、任意なら「〜してよい」、原則なら「原則〜する。例外は〜」
- 適用範囲を明示する。ある項目への指示は、書いていない他の項目には広がらない
- 自由度は作業の脆さに合わせる。失敗しやすい操作は正確なコマンドを示し、判断が要る作業は方針だけにする
- 選択肢を並べすぎず、既定の方法を 1 つ示して例外だけ添える
- 1 つの概念には 1 つの語を使い続ける
- RFC 2119 の解釈宣言のような、記法そのものの説明は書かない

## 疑似コードを併記する場面

条件分岐・ループ・カウンタ・状態のリセット・終了条件がある手順は、散文に加えて疑似コード（`pseudocode` か `text` のコードブロック）を書く。散文だけだと「いつ何を数え、いつリセットするか」の解釈がぶれる。

```pseudocode
attempt = 0
while not ci_passed():
  attempt += 1
  if attempt > 3:
    report_to_user(failures); stop
  fix(latest_failure)
```

## 種類別の注意

- skill の description: 何をするかといつ使うかを三人称で書き、主な用途を先頭に置く。"This skill should be used when" のような定型の前置きは書かない。副作用を伴い、人が実行タイミングを決めるもの（push、外部への投稿、永続状態の変更）は `disable-model-invocation: true` にし、自然文のトリガーは書かない。ユーザーが自然文で頼む作業でも同じである。ローカルファイルの編集は副作用に含めない。commit の作成そのものが目的の skill は、公式の `/commit` の例どおり `disable-model-invocation: true` にする（作業に付随するだけの commit は含めない）
- 参照の配置: SKILL.md は 500 行未満にし、詳細は skill ディレクトリ内の参照ファイルに分けて SKILL.md から直接リンクする。参照の参照は部分的にしか読まれないことがあるので 1 階層までにする。100 行を超える参照ファイルには冒頭に目次を置く
- AGENTS.md / CLAUDE.md: 200 行未満を目安にし、コードを読めば分かること（ディレクトリ構成、依存一覧）や一部の作業でしか効かない手順は skill へ移す
- hook がモデルに渡す文言: 何が起きたか・何が分かったかと、その理由を事実として短く書き、代わりにとる行動を 1 文で添える。system 命令風の強い文面にはしない
- レビュー系の指示: 「重大なものだけ報告」のように絞ると、見つけても報告しなくなる。全件を confidence と severity 付きで出させ、絞り込みは別の段階で行う
- 長時間の自律作業: 残作業はチェックリスト（TodoWrite、または TaskCreate / TaskUpdate、あるいはファイル）で管理させ、ユーザーの入力がないと進めないときだけ止まるよう書く
- 成果物ファイル: 長さは作業に必要な分だけにし、水増しの節・重複する要約・定型文を入れないよう書く
- フロントエンドの見た目: 「AI っぽくしない」のような一般論ではなく、避けるパターンや従うデザインシステムを具体的に書く
- MCP ツールは完全修飾名（`mcp__server__tool`）で書く
- サブエージェントへの委譲: 使わせるのは、並列化できる大きな作業か、文脈を分けたい作業（独立性が目的のレビュー、単位ごとの逐次処理など）に限ると書く。現行モデルは委譲しやすく、小さな作業や念のための再確認まで委譲すると遅く高くなる。独立性が目的のレビューでは、会話履歴を引き継ぐ fork ではなく `subagent_type`（`general-purpose` など）を明示して起動させる

## 既存の文書を直す手順

1. 対象を読み、各行を「消しても挙動が変わらない」「hook・lint・スクリプトにすべき」「書き直す」「残す」に分ける
2. 消す行を消し、機械化すべき行はその旨をユーザーに提案する
3. 残す行を上の形（条件 → 行動 → 理由、平叙文、肯定形）に書き直し、状態遷移のある手順には疑似コードを足す
4. 変更点を「削除 / 機械化の提案 / 書き直し」に分けて報告する
