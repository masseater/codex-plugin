# インタビュー

入力: `$ARGUMENTS`

## モードの選び方

- 引数が計画・仕様などのファイルを指す、または会話中に詰めるべき計画がある: 不明点を詰めるモード
- それ以外（要望が断片的、何をしたいかが言葉にならない）: 要件を引き出すモード

## 質問の作り方（両モード共通）

- 質問はすべて `AskUserQuestion` で行う。選択肢があるとユーザーは答えやすく、回答の解釈もぶれない
- 確認事項を 1 問にまとめず、事項ごとに別の質問にする。「A・B・C をどうするか」を 1 問にすると「A は採用、B は不採用」のような組み合わせを選べないため
- 1 回の呼び出しで最大 4 問まで同時に聞く。5 問以上あれば先に 4 問を聞き、残りは回答を受けてから聞く
- 各質問には具体的な選択肢を 2〜4 個付け、description にその選択の意味（長所・短所、回答後に編集するファイルと箇所）を書く。「その他」は自動で付くので選択肢に入れない
- 複数選択（`multiSelect`）は、答えが本当に排他的でないときだけ使う
- プロジェクトの規約や既存コードがあれば、それに沿った選択肢を作る

## 要件を引き出すモード

「何がしたいか」を言葉にできない人も、困りごと、避けたいこと、具体案への反応、似たものは答えられる。この 4 つの経路で周辺から聞き、「何がしたいですか」とは聞かない。

```text
if $ARGUMENTS is empty:
  ask 1 question: "何に困っていますか / 何をしたいですか（断片的で構いません）"
     with 3-4 starting points from the project context (既存機能の改善 / 新機能 / 問題の解決 / 作業の自動化)

round = 0
loop:
  unclear = what is still unclear in accumulated context
  if unclear is empty: break
  round += 1
  ask up to 4 questions with the highest information gain, in topic order:
    困りごと → きっかけ → 範囲（誰が・どこまで）→ 避けたいこと → 成功の条件 → 似たもの
  if round >= 5:
    summarize current understanding and ask "続けますか / ここまでで十分ですか"
    if sufficient: break
```

- WHAT と WHY を聞き、技術・設計などの HOW は聞かない。解決策を提案しない
- ユーザーの語彙をそのまま使い、専門用語に言い換えない
- 可能性を消すために「これは求めていない」という否定の選択肢を入れてよい

収束したら次の形でまとめ、「合っている / 微修正したい / もう一度整理したい」の 3 択で確認する。微修正なら該当点を、整理し直すならこれまでの文脈を保ったまま、ループに戻る。合っていれば、このまとめを次の作業にそのまま使えるプロンプトとして出力する。

```markdown
## 引き出した要件

### やりたいこと

<1〜3 文。ユーザーの語彙で>

### 背景・動機

### スコープ

<含むもの / 含まないもの>

### 制約

### 成功の条件

<観測できる結果>

### 参考
```

## 不明点を詰めるモード

1. 対象の文書を読み、決まっていない点・解釈が割れる点・矛盾を洗い出す。観点はプロダクト仕様・技術的詳細・UI/UX に限らない
2. 決定に影響の大きい順に、上の規則で質問する
3. 回答を対象の文書に反映する
4. 反映後の文書を読み直し、回答で新たに生じた不明点があれば 2 に戻る。ユーザーが「ここまでで十分」と言ったら止める
5. 決まったことを「決定事項（理由）」と「次にやること」の箇条書きで報告する
