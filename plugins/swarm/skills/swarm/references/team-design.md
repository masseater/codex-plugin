# role の設計

## 原則

role は専門性・視点で定義し、成果物で分けない。成果物で分ける（「skill 担当」と「hook 担当」）と、各成果物を 1 つの視点でしか見ない。視点で分ける（「ドメイン専門家」と「UX 担当」）と、どの成果物も複数の視点でレビューされ、単一視点では見えない欠陥が表に出る。

良い role の条件:

- 専門性・視点で定義されている（「フロントエンド開発者」ではなく「ユーザビリティの専門家」）
- 全成果物を横断して見る
- 他の role と補い合う（セキュリティと性能は別のものを見る）

## role テンプレート

調査:

- `{domain}-domain-expert` — 対象技術に非自明な仕様や制約があるとき。API・制限・エッジケースを担う
- `{ecosystem}-ecosystem-specialist` — 参考にすべき先行事例があるとき。既存ツールや慣習のパターンを担う
- `hypothesis-tester` — 原因の仮説が複数あるバグ調査。1 つの仮説を検証し、他の仮説の反証を試みる

設計・品質:

- `user-experience-strategist` — 利用者との接点があるとき。利用の流れ、情報設計、エラーメッセージを担う
- `tech-lead` — 複数の専門家の調整が要るとき。知見を設計判断に統合する（ファイルは直接編集しない）
- `devils-advocate` — 同調圧力のリスクが高いとき。前提を疑い、現在の方向に反論して根拠を強くさせる
- `naive-user` — 発見しやすさや導入のしやすさが重要なとき。前提知識なしで理解・利用できるかを確かめる
- `consistency-checker` — 規約が確立しているとき。用語・インターフェース形式・命名の揺れを確かめる

実装:

- `{stack}-specialist` — フレームワークの深い知識が要るとき
- `test-engineer` — 検証可能な受け入れ条件があるとき。テストを書いて実行し、カバレッジの穴を報告する

## 例: 新しい Claude Code プラグインの設計

- claude-code-domain-expert — plugin API、skill / hook / agent の仕様と規約
- plugin-ecosystem-specialist — 既存プラグイン、類似ツール、再利用できるパターン
- ux-strategist — 利用の流れ、起動条件、エラーメッセージ、命名
- devils-advocate — 設計判断に反論し、エッジケースを探す

## 例: 本番障害の調査

- hypothesis-network — タイムアウト、DNS、ロードバランサ
- hypothesis-application — メモリリーク、競合状態、設定のずれ
- hypothesis-infrastructure — ディスク、CPU、コンテナの制限

各 teammate が互いの結論に積極的に反証を試みるようにする。

## アンチパターン

- 成果物・層・ファイルごとの担当分け。横断レビューがなくなる。視点で分けた role が全体を見るように組み替える
- 6 人以上のチーム。調整コストが利点を上回る。焦点の定まった 3 人の方が成果を出しやすい
- 同じファイルの共同編集。上書きが起きる。担当ファイルを分け、横断レビューは読み取り専用の role に任せる
- 曖昧な spawn prompt。「認証モジュールを実装して」だけでは、技術スタック・場所・制約が分からず汎用的な出力になる
